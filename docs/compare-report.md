# 增强提示词质量对比：我们 vs WorkBuddy

## 对比口径

WorkBuddy 桌面端的「增强提示词」在实现上只有一步：把用户草稿塞进 `Yr` 模板，连同 `Jr` 系统提示词交给一次 `runAgent({agentName:"enhance-prompt"})`。它没有别的加工、没有后处理（只去一次包裹引号）。所以**用同一台模型分别跑两套提示词，比的就是提示词本身的质量**——这正是本对比做的事。

- 基准 A：`WORKBUDDY_SYSTEM` + `WORKBUDDY_USER_TEMPLATE`（从 `server.js` 逐字切出）
- 候选 B：`ENHANCED_SYSTEM` + `ENHANCED_USER_TEMPLATE`（自写，见 `lib/prompts.js`）
- 模型：`group/deepseek`（本机 magpie 网关），temperature 0.3，max_tokens 2000
- 用例：12 条，覆盖 中文/英文/中英混排 × 极含糊/已很具体 × 提问/列表/代码块/写作/运维
- 裁判：五轴各 1–5（fidelity 保真 / gain 具体化增益 / language 语言跟随 / restraint 不越界 / usable 可直接粘贴），每轮按 (用例序号+轮次) 奇偶交换 A/B 位置，多轮取均值以压掉位置偏好与噪声
- 确定性指标（不依赖裁判模型，可机器复核）：语言一致数、meta 泄漏、围栏、包裹引号、长度比、mustKeep 事实丢失数

## WorkBuddy 提示词的四个结构性短板（实测）

1. **灌水换分**：平均把 5 字的输入扩成 12 倍长度，常加原文没有的要求（robots.txt、退出码、应急处置、篇幅上限），restraint 恒在 3.1–3.6，是它最大的失分项。
2. **丢事实**：`src/queue.ts`、`src/utils/date.ts`、`5 attempts` 这类具体约束会掉，12 个用例里稳定丢 3–4 个（我们 0–1 个）。
3. **混排语言被翻平**：中英混排输入经常被整段译成中文，原文那句英文消失（我们 12/12 保语言，它 10–12/12 波动）。
4. **没有长度分档**：既会把已很具体的需求再灌一倍，也会把极短需求灌到 20 倍以上。

## 我们改了什么

| 规则 | 解决什么 | 证据 |
| --- | --- | --- |
| 1 语言逐字保留 | 混排被翻平 | R6 语言 4.98 vs 4.78；langOk 12/12 |
| 2 事实守恒（路径/标识符/数字/代码逐字） | 丢具体约束 | missingFacts 1 vs 3 |
| 3 保留原动作 + 三件白名单 + 输出前自检 | 越界加戏、把祈使句改成求建议 | restraint 4.35 vs 3.1 |
| 4 保留形态（提问仍是提问、列表仍是列表） | 提问被改成需求、列表被打散 | zh-question/zh-list 均胜 |
| 5 禁止把可做任务变成问卷 | 「请先补充」式回问 | R2 的 5 个失分用例在 R5 全部修复 |
| 6 长度按输入分档 | 5 字灌成 12 倍 | 5.64× vs 12.3× |
| 7 输出纪律 + 8 幂等 | 前言/围栏/重复增强继续膨胀 | fence/wrapped 0 |
